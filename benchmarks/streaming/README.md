# Streaming benchmark

The streaming study: does computing a rolling signature by *updating* it beat
recomputing it, and what does the update cost in accuracy?

This directory is research code. It is deliberately *not* part of the
installable `rollsig` package — it consumes `rollsig`'s public API exactly
as an outside user would.

```bash
uv run python -m benchmarks.streaming.bench                 # ~15 min, writes results/
uv run python -m benchmarks.streaming.bench --budget 0.25   # quick, noisier
uv run python -m benchmarks.streaming.bench --skip-roughpy  # omit the slow backend
```

Everything runs on synthetic random-walk paths, because all of the questions
are about arithmetic rather than about any dataset. The one exception is the
nested-window study, which reproduces the 600/300/150-second geometry and
channel count that `benchmarks/orvp` actually uses.

## What is being claimed

`rollsig.streaming` slides a window by cancelling the departing increment
with a group inverse and appending the arriving one, instead of re-reading the
window (`docs/notes-streaming.html` §10.1):

    S(next window) = S(departing)⁻¹ · S(window) · S(arriving)

Neither factor depends on the window length, so the per-tick cost should be
**flat in `window`** once the window is full. That is the claim. It is a
theorem, so a measured slope would mean a bug — which makes study 1 a
correctness check as much as a performance one.

Everything below is a **steady-state** measurement, taken after the window has
filled. That is the regime the claim is about: with time augmentation the
warm-up recomputes on every tick (the local [0, 1] time scale changes as points
arrive), so it is O(window) per tick until the window is full, and O(1) per
tick — O(1) amortized with re-anchoring on — thereafter.

## The three questions, and their answers

| Question | Answer |
| --- | --- |
| Is steady-state per-tick cost independent of the window? | **Yes.** 127 → 135 µs as the window goes 10 → 1200 at depth 2; 203 → 202 µs at depth 3. |
| Does it beat recomputing? | **Against RoughPy, the default backend, at every window measured** — 1.7× at window 10 rising to **129× at window 1200**. Against the numpy reference, by more (452×), but that is a test oracle. **Against compiled `iisignature`, only past a crossover** — window 1200 at depth 2, window 600 at depth 3. |
| What does it cost in accuracy? | Drift grows ~3 orders of magnitude per level of depth and ~quadratically in unanchored ticks. Re-anchoring once per window pins it at 7e-15 at every depth, for a 23–37% surcharge. |

Full numbers: [`results/streaming_table.md`](results/streaming_table.md) and
`results/streaming.json`. Both are regenerated by the command above; the
committed copies were produced on Linux 6.18.39 x86_64, Python 3.14.6, numpy 2.5.1.

### 1. Is the steady-state per-tick cost flat in the window?

Per-tick cost in the steady state, after the window has filled — one
channel, time-augmented and lead-lagged, the configuration
`benchmarks/orvp` feeds its signature arm:

| depth | window | streaming | + auto refresh | batch numpy | batch `iisignature` | batch RoughPy |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 10 | 127.0 | 157.4 | 458.8 | 22.4 | 216.3 |
| 2 | 300 | 130.3 | 173.4 | 14146.0 | 71.8 | 3280.7 |
| 2 | 1200 | 135.0 | 178.8 | 60000.1 | 231.4 | 13291.2 |
| 3 | 10 | 203.0 | 249.5 | 722.5 | 27.1 | 528.0 |
| 3 | 300 | 194.4 | 265.8 | 22483.7 | 172.5 | 6673.0 |
| 3 | 1200 | 201.9 | 264.6 | 91302.8 | 628.0 | 25987.6 |

A 120× change in window length moves the streaming column by under 6%, with
no consistent sign; the recompute columns move by the factor the window does.
That is the claim, measured.

`+ auto refresh` is the default configuration, which re-anchors on a
from-scratch recomputation once per `window` ticks (question 3). One O(window)
recompute per window ticks keeps the steady state O(1) amortised, and it shows
up as a flat 23–37% surcharge that also does not grow with the window.

### 2. Does it beat recomputing?

Against **RoughPy**, the library's default backend, at every window measured —
1.7× at window 10 rising to **129× at window 1200**, and still rising, since
one column is flat and the other is not. That is the headline comparison: it is
against the backend `rollsig` actually ships with.

Against the pure-numpy reference the ratio is larger (up to 452×) and means
less — numpy here is a test oracle, not a backend anyone should compute with.

Against `iisignature`, which is compiled C, **not always**. The streaming
update is interpreted Python making dozens of small numpy calls, and that
interpreter overhead is essentially its entire cost. The crossover:

| depth | `iisignature` wins below | streaming wins above |
| ---: | ---: | ---: |
| 2 | window 600 (125 µs vs 132) | window 1200 (231 µs vs 135) |
| 3 | window 300 (173 µs vs 194) | window 600 (326 µs vs 197) |

`method="auto"` uses this table only for the measured ORVP-style
configuration: four transformed channels at depth 2 or 3. With
`backend="iisignature"` it recomputes below the measured crossover window
(1200 at depth 2, 600 at depth 3) and streams at or above it; an unmeasured
dimension or depth conservatively uses batch. Against RoughPy and numpy it
streams everywhere because it won at every measured window. These are
benchmark-derived choices from the committed environment, not
hardware-independent guarantees. The `crossover_window` entry in
`results/streaming.json` is the source of the iisignature constants, and
`tests/test_streaming.py` pins the two together. The two routes agree to
floating-point noise either way, and an explicit `method="batch"` or
`method="streaming"` overrides the heuristic.

A compiled implementation of the same identity would move the crossover to a
very small window. That is deliberately not done here — `rollsig`'s stated
non-goals include reimplementing low-level signature computation, and the
value of `rollsig.algebra` is that the algebra is legible.

### 3. What does the update cost in accuracy?

Repeated group operations accumulate floating-point error a recomputation
never incurs. Measured as an infinity-norm ratio against a from-scratch
signature of the same window (absolute error alone is meaningless — a path
with large total variation has a large signature, and both grow together),
window 250, 20,000 ticks:

| depth | re-anchoring | relative drift | worst level |
| ---: | --- | ---: | --- |
| 2 | never | 8.3e-16 | 1.7e-15 (level 2) |
| 3 | never | 5.4e-13 | 3.2e-12 (level 3) |
| 4 | never | 4.2e-11 | 1.0e-09 (level 4) |
| 5 | never | 1.7e-09 | 2.0e-07 (level 5) |
| 2–5 | every 250 | 6.8e-17 – 6.9e-15 | ≤ 3.6e-13 |

Three findings:

1. **Depth is the axis that matters** — roughly three orders of magnitude per
   extra level. Level *k* of a product is a sum over every way to split *k*,
   so its rounding error is fed by every level beneath it, while its own
   coordinates are the smallest.
2. **Growth in time is quadratic, not square-root.** Doubling the unanchored
   tick count multiplies drift by about four, consistently, from 4.4e-13 at
   2,500 ticks to 1.7e-10 at 40,000. A long-running stream does not grow out
   of it.
3. **Path scale is second-order and non-monotone.** Over four orders of
   magnitude of increment size the depth-4 drift moves by about 200× and then
   back down at the largest scale, as the price channel comes to dominate the
   time channel and the signature's own magnitude outgrows the error.

Re-anchoring on a from-scratch recomputation every `window` ticks keeps the
steady state O(1) amortised and pins the drift at 7e-15 at *every* depth.
That is why `refresh_every="auto"` is the default rather than an option for
the cautious; `refresh_every=None` exists so this study can measure the raw
drift.

### 4. The nested-window study, and a retraction

`docs/notes-orvp.html` §9.1 proposed removing the redundancy in ORVP's nested
600/300/150-second windows by left-multiplying the full window's signature by
the inverse of each departing prefix. That identity is correct and the
algorithm is not a saving: it needs the full window's signature *and* every
prefix's, which is the same 1,050 points of path the naive route walks.

The saving comes from cutting the longest window into **disjoint** chunks at
the shorter windows' boundaries and combining them right-to-left with Chen's
identity — 600 points, each read once, no inverse. `nested_suffix_signatures`
does that, with an `algebra.dilate` fix-up for the fact that `time_augment`
normalises its channel per window.

| route for 600/300/150 | ms per segment |
| --- | ---: |
| naive — three independent signatures (numpy) | 76.74 |
| Chen — disjoint chunks combined (numpy) | 46.43 |
| naive — three independent signatures (`iisignature`) | 0.58 |

All three agree to 3e-15.

The chunked route saves what the point count says it should: 1.65× where
1050/600 = 1.75× is the ceiling, the gap being the tensor multiplications that
stitch the chunks together. And then the number that settles it — calling
`iisignature` three times does the whole job 80× faster than either numpy
route. **For ORVP's feature build the right answer is to call the compiled
backend three times and not be clever.** The chunked route is worth having
when the backend is the numpy one, and would be worth having again if the
algebra were compiled; neither is where this benchmark sits.

## Reading the results honestly

- **The asymptotic claim is the strong one and it holds — in the steady
  state.** Steady-state per-tick cost independent of window length is a
  statement about the algebra, and it is what the streaming column measures.
  It is not a claim about every update from tick 1: under time augmentation
  the warm-up recomputes, at O(window) a tick, until the window fills.
- **The wall-clock claim is conditional and is stated as such.** The update is
  interpreted Python; against a compiled batch backend it wins only past a
  crossover window. The defensible headline is the 129× over RoughPy at
  window 1200, together with the flatness — quoting the 452× against the numpy
  reference, or any speedup, without the `iisignature` qualification beside it
  would be dishonest, so the `iisignature` column is in every table.
- **Drift is real, bounded, and priced.** It is not "negligible" in the
  hand-waving sense — at depth 5 without re-anchoring it is measurable. It is
  negligible *after* re-anchoring, which is why re-anchoring is the default
  rather than an option.
- **Synthetic paths are a limitation.** The timings are properties of the
  arithmetic and would not change on real data, but the drift figures depend
  on the increment distribution. The scale sweep in `results/streaming.json`
  is the sensitivity check for that, and it moves very little.
