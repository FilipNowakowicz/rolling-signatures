## What this repo is

A standalone, public Python package installed from this repository (not
PyPI, by choice): a `scikit-learn`-compatible transformer that turns
financial time series into **path signature** features, plus a streaming
engine that slides the window at O(1) steady-state cost per tick.

It is the **flagship CV project** — the one with the most detail, the one
Filip can talk through for 20 minutes in an interview — not another
closed-loop backtest. Two prior projects already cover derivatives pricing
and systematic backtesting (see "Relationship to `quant`" below); they are
finished and were never folded into this one. This project's job was to
demonstrate something different: real open-source research software, built
on the specific pure-math strength (rings/algebras) rather than generic
quant-finance plumbing.

### Why signatures, specifically

The signature of a path lives in the tensor algebra
$T((V)) = \bigoplus_n V^{\otimes n}$ — a noncommutative associative ring
under the tensor product. The log-signature lives in the free Lie algebra
generated by $V$. Signatures satisfy Chen's identity (concatenation ↔ tensor
product) and the shuffle-product identity (a Hopf algebra structure — a
commutative ring dual to the tensor algebra). This is a direct application
of free-algebra/ring-theory machinery, not decoration — those identities are
also how correctness gets verified in tests, and Chen's identity plus the
group inverse are what make the streaming update constant-cost.

### The positioning, and the honesty constraint on it

Fast low-level compute libraries already exist (`iisignature`, `RoughPy`,
`signax`, `esig`) — bare tensor-algebra primitives with no finance framing.
**`sktime` already ships a `SignatureTransformer`** (Generalised Signature
Method, Morrill et al. 2020), so "nobody packaged signatures" is false and
must never be claimed anywhere. The gap the README states precisely: sktime
targets panel classification (pre-segmented series → one vector); quant
pipelines need *causal rolling-window features on a continuous stream* with
strict no-lookahead alignment, finance-specific preprocessing defaults
(lead-lag → quadratic variation), and sliding-window updates that cost O(1)
per tick in the steady state — which no high-level library exposes. The
streaming engine is the genuine mathematical contribution.

### What the results actually were

Both headline claims are in the README with their numbers; keep any future
summary consistent with them, including the negative one:

- **Streaming engine — positive.** Steady-state per-tick cost flat across a
  120× change in window length; 129× over RoughPy at window 1200; wins over
  compiled `iisignature` only past a measured crossover, which
  `method="auto"` encodes. Drift measured and priced; re-anchoring on by
  default.
- **ORVP benchmark — negative.** Signature features did not beat reproduced
  order-book baselines, on three pre-registered stock subsets, including
  after the order-book state was given to them as extra path channels.

Claims about complexity are stated in a fixed form and should stay that way:
O(1) *steady-state* per tick once the window is full, O(1) *amortized* with
periodic re-anchoring, and a warm-up that is explicitly not constant-time
under time augmentation.

## Research standards (carried over from `quant`)

- Strict temporal discipline: no lookahead, enforced by test rather than
  assumed
- Transaction costs included in any backtest that trades
- Honest conclusions — if signature features don't beat the baseline, that
  goes in the README as prominently as a win would have
- Comparisons hold the learner and the folds fixed and change only the
  input columns, so a difference is a statement about features

## Working in this repo

- Package name is `rollsig`; repository name is `rolling-signatures`.
- `RoughPy` is the default backend, `iisignature` an optional extra, numpy
  a test oracle only. All three sit behind `rollsig._backend`.
- The two `benchmarks/` directories are research code, outside the
  installable package on purpose — they consume the public API as an
  outside user would. Their committed `results/` are the deliverable and
  are not regenerated casually; regenerating requires the ORVP data on disk
  and hours of compute.
- The `docs/*.html` notes are a chapter-by-chapter build journal. Their
  chapter-local status tables are historically accurate as of that chapter
  and should not be retro-edited into a false present tense.
- Tests: `pytest -q` (150 tests, CI on Python 3.11 and 3.12).
